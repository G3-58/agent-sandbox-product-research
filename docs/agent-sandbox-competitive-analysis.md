## 核心结论

**研究判断：Agent Sandbox 的竞争正在从单点执行能力，延伸到计费口径、接入体验和治理能力。企业内部平台应复用成熟底座，把差异化放在 AI 网关和平台运营。**

1. **隔离路线在收敛，但尚未完全同构。** 多家厂商采用 microVM；Daytona 默认提供容器类 Sandbox，Modal 同时提供 gVisor 与 VM 路线。运行时类别、安全默认值和可配置边界，不能只用一个“安全”标签概括。
2. **E2B 兼容生态值得优先关注。** 阿里云和腾讯云相关产品提供 E2B SDK 兼容路径。这支持“接入层正在趋向通用”的判断，但不足以证明它是覆盖全行业的正式标准，也不意味着高级能力能直接迁移。
3. **高空闲占比下，计费口径可能比单价更影响账单。** 按存活时长计费、按活跃 CPU 计费和自动休眠会产生不同成本。CPU 停止计费不等于内存、存储和平台服务费同时归零。
4. **云厂商正在从沙箱走向 Agent 运行时平台。** AWS AgentCore、腾讯云 Agent Runtime、阿里云 AgentRun 和火山引擎 AgentKit 均把执行环境与身份、网关或观测等能力结合，但各家产品边界并不相同。
5. **对 NEX 这类内部平台的建议：** P0 聚焦核心接入兼容、安全默认值和分级回收；P1 完善网关、身份、成本归属与可观测；P2 再建设模板生态和分场景文档。

以上结论是公开资料基础上的产品分析，不代表对任何公司内部架构、路线图或实际运行效果的了解。

## 1. 分析背景与评估框架

Agent 会自己写代码、跑命令、安装依赖、访问网络。这些动作不应无边界地直接落在业务服务器上。Sandbox 的作用，是为 Agent 提供可隔离、可回收的执行环境，并使权限、资源和状态的边界可管理。

与传统 Serverless 相比，Agent 负载有三个特点：

- **代码不可信：** 执行的是模型生成或外部引入的代码，隔离与权限是底线要求。
- **会话长且有状态：** 任务可能持续数十分钟甚至更久，需要保存进度、恢复执行，有时还需要分叉并行尝试。
- **等待时间长：** 在等待模型、工具和网络时，CPU 可能空闲；存活时长与实际消耗的计费差异因此更显著。

本文从六个维度比较。前五项对应开发者接入决策，第六项对应企业平台运营诉求。

| 维度 | 关注问题 | 产品意义 |
| --- | --- | --- |
| 隔离方式 | microVM、gVisor 或容器；默认策略是什么 | 不可信代码的运行边界、兼容性与安全责任 |
| 创建与恢复时延 | 新建、预热池分配、恢复分别多久 | 交互首响应、批量创建吞吐及长任务续跑体验 |
| 状态持久化 | 内存、文件系统、进程；暂停、快照、fork | 能否续跑、回滚及复用环境 |
| SDK 与接入成本 | 语言支持、镜像定制、兼容边界 | 内部团队迁移和接入门槛 |
| 计费模式 | 存活时长或实际消耗；暂停后哪些资源收费 | 高空闲占比下的真实成本 |
| 平台与治理 | 出口网络、身份、配额、审计、观测、私有化 | 企业生产接入、安全控制、成本归属与问题排查 |

## 2. 对比总览

### 2.1 能力对比

**所有时延均为厂商宣称或原稿资料记录，不是统一环境下的实测。** 新建、恢复、预热分配、单并发和批量创建需要分开看；“未列出”也不等于厂商没有该能力。

| 产品 | 隔离方式 | 时延参考 | 状态与生命周期 | 接入与部署 |
| --- | --- | --- | --- | --- |
| E2B | Firecracker microVM | 原稿记录恢复约 1 秒；不与新建时延横比 | 暂停保留内存与文件系统；支持 snapshot、fork；Hobby 会话最长 1 小时，Pro 24 小时 | Python、JS/TS；运行时开源，企业版 BYOC |
| Daytona | 默认容器，另有 VM 类 | 容器类官方宣称低于 90ms | 容器 stop 与 VM pause 的状态保存不同；闲置停止策略可配置 | Python、TS、Ruby、Go、Java；企业版 BYOC |
| Modal | gVisor，也提供 VM 运行时 | 本文不列统一创建时延 | 文件系统/目录快照；内存快照与运行时、版本和开放范围有关；原稿记录默认 5 分钟、最长 24 小时 | Python、JS、Go；托管算力平台 |
| AWS AgentCore | Runtime microVM 与 Instances 两类计算形态 | 本文不列统一创建时延 | 原稿记录 microVM 会话 8 小时、Instances 14 天；适用计算类型及限制需分别确认 | SDK；MCP/A2A；Instances 位于客户 AWS 账号内的 EC2 |
| Vercel Sandbox | Firecracker microVM | 官方以毫秒级描述；不作排名 | 快照与恢复能力；原稿记录 Hobby 45 分钟、Pro 24 小时 | TS、Python；托管服务 |
| 阿里云 FC 云沙箱 | MicroVM；需区分 FC 实例隔离配置 | 原稿记录百毫秒冷启动，预热可更低 | 浅休眠和深休眠保存能力、费用与开通条件不同 | E2B 兼容端点；同时提供 FC Extensions |
| 腾讯云 Agent Runtime | VM 级隔离；开源 CubeSandbox 使用 RustVMM/KVM | 产品页宣称 100ms；CubeSandbox 另有测试口径 | 休眠、快照与持久化存储；Serverless 与常驻形态 | SDK/API/CLI/MCP；E2B 兼容；CubeSandbox 开源 |
| 火山引擎 AgentKit | 官方沙箱模板文档明确为 microVM | 本文未列可比创建时延 | 工具实例按会话管理；官方文档列出最长 24 小时 | VeADK、沙箱模板、工具 API；与 AgentKit 平台结合 |

需要特别注意：暂停保留内存、停止保留磁盘、创建镜像和保存目录，并不是同一种持久化能力。选型前应通过同一恢复测试确认进程、文件和外部连接的行为。

### 2.3 空闲时长为何影响成本

原稿的“空闲 50 分钟使月费涨 5～6 倍”需要限定场景。下面用透明假设替代缺失的原始图表，**只是计费模型示例，不是厂商实测**。

假设每次任务分配 1 vCPU、1 GiB，实际计算 10 分钟；CPU 与内存单价分别为 $0.0504/vCPU·时、$0.0162/GiB·时。不计存储、流量、套餐和税费。

| 模型 | 活跃 10 分钟即释放 | 再空闲 50 分钟 | 成本解释 |
| --- | --- | --- | --- |
| CPU 和内存均按存活时长 | $0.0111 | $0.0666 | 分配规格不变、存活从 10 分钟到 60 分钟，因此此项费用为原来的 6 倍 |
| CPU 仅按忙时、内存持续计费 | $0.0111 | $0.0246 | CPU 费用不增加，内存仍增加；不能写成“空闲不收费” |

若任务次数相同，上述计算资源费用比例可以延续到周期累计；加入套餐等固定费用后，总账单不一定仍是 6 倍。自动暂停还会引入快照存储、恢复时延与恢复失败风险，需要一起评估。

## 3. 海外主要产品

海外玩家可分为以 Sandbox 为主要产品的公司，以及把 Sandbox 作为云或开发平台组件的厂商。前者更强调接入与执行体验，后者强调生态整合和平台治理；这是一种产品定位分析，不是市场份额排序。

### 3.1 E2B：兼容生态的参照

- **定位：** 为模型生成代码提供独立 microVM 执行环境，能力覆盖代码执行、网络、存储及生命周期管理。
- **亮点：** 暂停/恢复、快照、fork；开源运行时与企业 BYOC。暂停保存状态和保存期限应以当时文档及套餐为准。
- **取舍：** Hobby 最长 1 小时；Pro 每月 $150，包含 100 并发并提供扩容档位；企业条件另议。[定价依据](https://e2b.dev/pricing)
- **产品判断：** 国内厂商的 E2B 兼容路径说明其开发接口有生态影响力。本文将“事实标准”视作分析简称，不把它写成正式标准认证或市场占有率结论。

### 3.2 Daytona：速度与语言覆盖

- **定位：** 可编程开发环境，默认 Linux 容器类，另提供 VM 类等运行形态；容器创建官方宣称低于 90ms。
- **亮点：** Python、TypeScript、Ruby、Go、Java SDK，以及 Git、LSP、Computer Use 等开发能力。
- **取舍：** 容器类和 VM 类的隔离、暂停、快照语义不同。停止后的文件系统保留不能等同于内存恢复。
- **启示：** 默认运行时和网络策略影响大多数用户实际获得的边界。应按负载和威胁模型评估，而不笼统声称“容器不安全”。[隔离说明](https://www.daytona.io/docs/en/isolation/)

原稿提到其开源仓库自 2026 年 6 月转向私有开发；本次没有独立核实这项历史变化，因此不将它作为选型结论的依据。

### 3.3 Modal Sandboxes：算力平台的延伸

- **定位：** Serverless 算力平台中的隔离执行能力，对已有 Modal 工作流的团队较自然。
- **亮点：** GPU Sandbox、gVisor 与 VM 运行时路线、快照能力；其中 GPU 支持和 VM 能力不能随意组合推定。
- **计费：** 秒级结算，按申请量与实际用量的较大值；CPU 申请单位为物理核。[资源说明](https://modal.com/docs/guide/sandbox-resources)
- **取舍：** 内存快照有运行时和开放范围限制，默认/最长运行时长及存储成本应按具体版本确认。原稿的“价格最高”“普通函数 3 倍”不作为跨厂商无条件排名。
- **安全：** 官方区分 gVisor 与 VM 边界，同时提供出口控制；默认可访问公网不等于缺乏可配置治理能力。[网络与安全](https://modal.com/docs/guide/sandbox-networking)

### 3.4 AWS Bedrock AgentCore：模块化运行时平台

- **定位：** 不仅提供代码工具，还托管 Agent 运行时；计算类型包括 microVM 和 Instances。
- **亮点：** microVM 按实际资源消耗计费，I/O 等待期间 CPU 可不收费；Instances 面向更持久或资源密集型负载，运行于客户账号的 EC2。
- **平台：** Runtime、Gateway、Identity、Memory、Observability、Evaluations 等模块可独立或组合使用，不能将所有能力和价格合并为单一“沙箱”。
- **取舍：** AWS 生态整合较深，功能模块、计算类型和计费项目也更多，实际选型需要梳理工作负载和成本归属。[官方定价及计算形态](https://aws.amazon.com/bedrock/agentcore/pricing/)

原稿记录 microVM 会话上限 8 小时、Instances 14 天。这些是特定计算形态限制，接入前应查看最新生命周期文档，不将文件持久化与会话上限混为一谈。

### 3.5 其他参照

- **Vercel Sandbox：** Firecracker microVM、快照和开发者平台整合；活跃 CPU 与预置内存分开收费。原稿记录 Pro 并发上限 1 万，具体配额以账号套餐与官方文档为准。
- **Cloudflare Sandbox SDK：** 与 Workers 编排生态结合。原稿记录 SDK 为 TypeScript、底层与容器/microVM 能力结合；本次未据此推定每一种部署形态都拥有相同的会话内核边界。
- **Northflank：** 可作为 BYOC 与部署平台路线的参照；原稿的“列表价最低”缺少同条件工作负载证明，不保留为确定排名。
- **Kubernetes Agent Sandbox：** 通过 `Sandbox`、`SandboxTemplate`、`SandboxClaim`、`SandboxWarmPool` 等资源管理隔离、有状态工作负载，运行时可替换；适合自建平台研究生命周期抽象与预热池。[项目仓库](https://github.com/kubernetes-sigs/agent-sandbox)

Kubernetes 开源项目、GKE 托管实现与各自网络默认策略需要分别核对，不能把某个托管版本策略当成整个开源项目的固定默认值。

## 4. 国内主要产品

国内产品的共同趋势是将隔离环境与 Agent 运行、工具、身份、治理组合，并提供降低接入成本的兼容路径。性能数字、开放范围和服务配额仍需按产品、地域和版本分别确认。

### 4.1 阿里云：一个底座，多个入口

- **FC 云沙箱：** 提供 E2B SDK 友好的接入方式。迁移需设置 API Key、API URL 与域名，并先验证创建、执行、文件读写和资源释放。[迁移说明](https://help.aliyun.com/zh/functioncompute/e2b-compatibility-and-migration)
- **兼容边界：** 不等同于完整 E2B。Snapshot、Volume、Team、网络、监控等需要确认具体兼容范围或 FC Extensions；API Key 管理也不能直接照搬。
- **休眠：** 浅休眠与深休眠的费用不同。FC 实例隔离文档说明浅休眠不收 vCPU 费，但内存仍收费；深休眠保留运行状态后释放实例，暂停期间不收 CPU/内存费，当前文档还有白名单及运行时条件。[浅休眠](https://www.alibabacloud.com/help/zh/functioncompute/overview-of-instance-isolation) · [深休眠](https://help.aliyun.com/en/functioncompute/sandbox-deep-hibernation-pause-and-resume-session)
- **其他入口：** 原稿还研究了 AgentRun、ACK Agent Sandbox、PAI-Sandbox，分别面向 Agent 平台、Kubernetes 和 AI 平台用户；不能把一条产品线能力自动归给另一条。

原稿记录约 99% SDK 兼容、单 Region 百万级并发、每分钟创建 10 万个实例，以及浅休眠约 1ms、深休眠约 1 秒和典型降本 60%～80%。这些作为厂商资料线索保留，不作本文实测结果；实际兼容、可用性、配额和成本需单独验证。

### 4.2 腾讯云：Agent Runtime 与 CubeSandbox

- **Agent Runtime：** 产品页围绕接入、运行、治理、智能四层组织能力，覆盖 SDK/API/CLI/MCP、沙箱与持久化、身份与网关、观测及记忆评估。
- **形态与场景：** 宣称 100ms 启动、数十万实例/分钟，并提供短时与常驻形态；覆盖在线应用、训练与评测，包含代码、浏览器、电脑等环境。[产品页](https://cloud.tencent.com/product/ags)
- **开源底座：** CubeSandbox 使用 RustVMM/KVM，并兼容 E2B SDK。仓库报告单并发裸金属测试低于 60ms，50 并发创建的平均与尾延迟另列；不能把单并发最优数字当成高并发 P99。[仓库与测试说明](https://github.com/TencentCloud/CubeSandbox)

原稿记录 MiniMax、腾讯元宝、面壁智能等客户案例。它们只作为厂商案例信息，不代表本文验证过客户部署、性能或采购效果。

### 4.3 火山引擎：AgentKit 平台内的沙箱工具

- **形态：** 通过沙箱模板提供 AIO、Code、Skills 等环境，由 Agent 在运行时调用；AIO 集成浏览器、终端及代码执行。[模板管理](https://docs.volcengine.com/docs/agentkit/Creating_tools?lang=zh)
- **隔离与生命周期：** 官方说明模板基于 microVM，实例按会话保留上下文，结束后回收，并列出最长运行 24 小时；原稿“未找到隔离说明”在公开发布时据此更新。[模板概述](https://docs.volcengine.com/docs/agentkit/Tool_overview?lang=zh)
- **平台边界：** 沙箱是 AgentKit 的工具运行环境组件，与身份、网关和其他基础设施整合，不宜仅按独立代码执行产品对比。

## 5. 市场洞察与趋势

### 5.1 安全默认值比技术标签更值得关注

microVM 正被多家产品采用，但 gVisor、容器和 VM 的组合仍存在。企业平台应明确：什么负载可以运行、默认是否允许公网、密钥如何提供、租户和资源边界如何验证，以及谁能例外放开权限。

因此本文倾向为不可信、多租场景优先评估硬件隔离，并采取最小权限与出口白名单。这是产品建议，不是声称某一运行时在所有场景都不安全。

### 5.2 E2B 兼容降低基础迁移成本，但没有消除产品差异

国内兼容产品说明 E2B 接口具有生态影响力。更严谨的验收方式不是“能改 Endpoint 就算兼容”，而是比较创建、执行、文件读写、超时、暂停恢复、快照、挂载、网络和鉴权等能力的兼容矩阵。

**分析判断：** 接口层容易被追随之后，差异化可能上移到高级生命周期、存储、治理、SLA 与内部支持能力。这个判断不等于已经证明接口层完全商品化。

### 5.3 回收策略是成本治理的抓手，但要识别“等待”

Agent 等待模型时 CPU 空闲，并不代表任务结束。仅靠 CPU 空闲率回收，可能终止仍然有效的会话。

更合适的产品策略是结合任务状态、心跳、工具调用和用户恢复意愿，分级执行保活、暂停、归档与销毁；同时分别记录等待时长、暂停时长、恢复耗时和存储占用。

### 5.4 运行时平台化，但 AI 网关与工具网关要区分

AWS、腾讯云、阿里云和火山引擎都在组合运行时与治理能力。内部平台可以借鉴这种组织方式，但不能把不同网关当成同一能力：

- **模型网关：** 多模型路由、模型访问凭证、Token/调用配额、费用归属等。
- **工具网关：** 工具注册、协议转换、工具调用权限、审计与凭证代理等。

NEX 的 AI 网关应先确认实际责任范围，再决定与 Sandbox 网络出口、身份服务及工具网关的边界；AWS 的工具 Gateway 不自动证明其覆盖同样的模型路由能力。

### 5.5 场景分化需要不同默认配置

| 场景 | 首要诉求 | 应重点测试 |
| --- | --- | --- |
| 在线 Agent | 首响应、恢复与稳定性 | 创建/恢复 P99、失败重试、网络与凭证策略 |
| 长任务 | 更长会话、状态保留、断点续跑 | 会话上限、暂停恢复正确性、存储和快照成本 |
| RL 训练与评测 | 批量创建、吞吐、配额与环境复现 | 并发创建尾延迟、预热池命中、模板版本及资源利用率 |

## 6. 对企业内部平台的启示

以下建议仅基于公开岗位中描述的 Sandbox 生命周期、AI 网关与平台运营方向，是个人方案，不是 NEX 已确定的路线图。

### 6.1 能力优先级

| 建议 | 竞品依据与产品取舍 | 优先级 |
| --- | --- | --- |
| 接入层提供核心 E2B SDK 兼容，并公开兼容矩阵 | 借鉴阿里云、腾讯云迁移路径，先验证基础闭环，不承诺所有高级 API 零改造迁移 | P0 |
| 为不可信负载设定隔离、出口网络和凭证的安全默认值 | 优先评估 microVM 等硬件隔离；出口默认拒绝并提供明确白名单及最小权限例外流程 | P0 |
| 创建/恢复、预热池与分级回收 | 先保证状态正确、失败可处理，再平衡预热成本和时延；不能仅凭 CPU 空闲销毁 | P0 |
| AI 网关与身份：统一模型代理、出口凭证注入、团队配额 | 区分模型网关和工具网关；借鉴运行时与 Identity/治理模块的协作方式 | P1 |
| 按在线、长任务、训练评测分档会话上限与规格 | 默认配置面向常见负载，同时为有依据的长任务和批量评测开放不同策略 | P1 |
| 成本归属、会话级观测和审计日志 | 关联团队、应用、任务与会话，支持成本定位、失败归因和异常追溯 | P1 |
| 镜像模板库与分场景接入指引 | 通过版本化环境、示例和排障文档降低接入负担 | P2 |

P0/P1/P2 是实施顺序建议，不代表忽略基础监控、日志和成本计量。P0 上线本身仍需具备最小可用的审计、告警和资源计量。

### 6.2 建议跟踪的指标

| 指标 | 口径建议 | 用途 |
| --- | --- | --- |
| 新团队接入耗时 | 从提交接入申请到第一个业务任务成功，区分排队和实际改造时间 | 衡量接入门槛 |
| 创建成功率 | 规定时间窗口内成功进入可执行状态的请求 / 合法创建请求 | 衡量基础可靠性 |
| 创建与恢复 P99 | 新建、预热分配、恢复分别统计，并标注规格和并发 | 避免不同路径混比 |
| 单任务平均成本 | 计算、内存、存储、流量及平台分摊费用 / 成功业务任务数 | 衡量实际业务成本 |
| 空闲资源占比 | 区分正在等待模型、无心跳闲置、暂停及预热池资源 | 找到可回收空间，降低误杀 |
| 安全事件数 | 按越权、异常出口、凭证暴露等分类，并记录影响与处理时间 | 明确安全底线 |

### 6.3 下一步验证计划

这部分是后续计划，不是已经完成的实验或用户访谈：

1. 收集内部团队的在线、长任务和评测三类典型流程，确认状态保留与网络需求。
2. 使用相同镜像、规格、地域与并发，分别测试创建、预热分配和恢复。
3. 设计中断、等待模型、凭证过期和网络受限用例，检查状态恢复与失败提示。
4. 用真实资源记录复算账单，验证节省来自减少存活、CPU 等待免计费还是内存回收。
5. 将能力选择转成兼容矩阵、验收条件和接入文档，再调整优先级。
